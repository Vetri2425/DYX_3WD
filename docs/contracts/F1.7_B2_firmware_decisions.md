## 13 · RoverLandDetector returns `true` unconditionally — DROP

- **Protected against:** "the land detector incorrectly gating rover auto-missions"
  (commit message; no field evidence recorded).
- **v1.17:** `src/modules/land_detector/RoverLandDetector.cpp` `_get_landed_state()` returns
  `!_armed` — an armed rover is *not landed* — plus AUTO_LAND/DESCEND and an RTL-arrival case.
- **Why drop:** the old patch *caused* row 14's bug: with the rover permanently "landed",
  `mission_block` never evaluated waypoint arrival (rover at 0.0 m from WP0, `seq_reached = -1`).
  Re-applying it would re-create that failure.

## 14 · `mission_block` `is_rover` waypoint-acceptance bypass — DROP

- **Protected against:** waypoint acceptance never firing while landed.
- **v1.17:** `src/modules/navigator/mission_block.cpp:162` evaluates arrival when not landed —
  correct with stock row 13. `:213` adds rover handling upstream: a TAKEOFF item is accepted on
  2D distance alone.
- **Why drop:** it existed only to undo row 13.

## The explicit-control contract (rows 15 P1/P3/P4 and 16 depend on it)

Path **A** (human decision 2026-10-07): OFFBOARD mode plus one firmware change —
`fix(rover_differential)` in `DifferentialOffboardMode::offboardControl()`: when no
`trajectory_setpoint` has been received, or its NED velocity is not finite, the velocity branch
no longer derives `speed = ‖v‖` / `yaw = atan2(vy, vx)`. The stock speed/attitude/rate
controllers then consume the companion's rover setpoints unmodified. A companion sending a
finite velocity gets unchanged stock behaviour.

The companion (`dyx3_px4_link`) publishes, every cycle, at ≥ 100 Hz over Ethernet DDS:

| | `offboard_control_mode` | `trajectory_setpoint.velocity` | `rover_speed_setpoint.speed_body_x` | `rover_attitude_setpoint.yaw_setpoint` | `rover_rate_setpoint.yaw_rate_setpoint` |
|---|---|---|---|---|---|
| STOP | `velocity=true` | NaN | 0 | NaN | 0 |
| TRACK_HEADING | `velocity=true` | NaN | v (signed) | ψ | — (attitude controller produces it) |
| TRACK_RATE | `velocity=true` | NaN | v (signed) | NaN | r |
| PIVOT | `velocity=true` | NaN | 0 | NaN | r |
| CREEP | `velocity=true` | NaN | low v | NaN | r |

Why each field:
- `velocity=true` is the only stock flag that enables speed + attitude + rate + allocation
  controllers together (`ModeUtil/control_mode.cpp`).
- `trajectory_setpoint.velocity = NaN` must be **published every cycle** during explicit control.
  uORB retains the last published `trajectory_setpoint`: if a finite velocity was ever sent and
  publication then simply stops, the firmware keeps seeing that finite value and the stock
  `‖v‖` / `atan2` adapter overwrites the direct setpoints.
- `yaw_setpoint = NaN` releases the attitude controller: `DifferentialAttControl` only publishes
  a rate setpoint while its cached yaw is finite, and the cache persists until a new value
  arrives — so NaN must be **sent**, not merely omitted.
- Controllers cache the last setpoint. Freshness is enforced by the commander's OFFBOARD loss
  check on `offboard_control_mode` (`offboardCheck.cpp`): `COM_OF_LOSS_T` + `COM_OBL_RC_ACT`.

**Companion obligation (F-tasks A1.1 #2):** stop publishing `offboard_control_mode` the instant
RPP output goes stale — a live heartbeat with stale setpoints is the one hole the commander
check cannot see.

> **OPEN — human value required:** `COM_OF_LOSS_T` (stock 1.0 s; min 0, 0.01 s steps) and
> `COM_OBL_RC_ACT` (proposed 5 = Hold). At ≥ 100 Hz a value of 0.1–0.2 s is the expected range.
> Not set here: a tuning value must come from a human or field evidence (CLAUDE.md §4).

**Acceptance:** spec GATE 1 on the bench — STOP, TRACK_HEADING, TRACK_RATE, PIVOT, CREEP and
reverse each drive the vehicle as described, no `DifferentialOffboardMode` republish is observed in the ulog, and the
kill-companion stop distance is measured (F5 / A1.1). Passing GATE 1 closes rows 15 and 16.
